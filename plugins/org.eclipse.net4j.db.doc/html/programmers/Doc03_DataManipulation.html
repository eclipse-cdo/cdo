Data Manipulation

  

Author: Eike Stepper

Net4j DB's structured DML API represents statements as schema-aware definitions, compiles them for an adapter, and binds application values to prepared JDBC statements. A template is independent of a connection. Its compiled statement records rendered SQL and ordered parameter occurrences, while a managed connection prepares and caches JDBC statements. The caller owns each prepared statement checkout and its result sets.

The fluent interfaces constrain clause order and keep identifiers connected to schema metadata. Parameter objects keep values separate from SQL text. Structured fragments can combine raw SQL with structured expressions, but raw fragment text remains trusted input and is not made portable or safe automatically.

Most examples use a SALES schema containing CUSTOMER(ID, NAME, EMAIL) and ORDERS(ID, CUSTOMER_ID, TOTAL, STATUS). Snippets accept schema objects and managed resources as method arguments; they do not create a database or define an application's transaction policy.

1  Introduction

Author: Eike Stepper

Structured DML separates statement shape from values and connection state. This makes definitions composable and reusable while leaving connection ownership and transaction boundaries with the application.

1.1  Concepts and Architecture

Author: Eike Stepper

SQL creates expressions, conditions, fragments, parameters, and statement builders. An SQLTemplate is the immutable adapter-neutral definition captured by build(). Compiling it with an IDBAdapter produces an SQLStatement containing rendered SQL and metadata for each JDBC parameter occurrence. An IDBConnection prepares that SQL and returns a managed IDBPreparedStatement; execution and result reading use JDBC through the Net4j DB wrappers.

An SQLExpression represents a value and an SQLCondition represents a predicate. Staged interfaces in org.eclipse.net4j.db.dml.fluent expose the next legal operation. Builders are mutable while assembled, but an earlier stage becomes stale after advancing. Each call to build() captures its own snapshot, so later valid changes do not rewrite an earlier template.

1.2  The DML Lifecycle

Author: Eike Stepper

A typical operation creates a template from schema objects, compiles it once for the selected adapter, prepares it on a managed connection, binds all required values, executes it, and closes the result set and statement. Closing a managed prepared statement returns it to that connection's cache. A template or compiled statement can be reused independently of a checked-out JDBC statement.

Binding calls can change some JDBC positions before a later converter or setter fails. Net4j DB validates structural ranges before starting a sequence, but it cannot undo JDBC side effects already performed by an earlier binding operation. Transaction rollback remains the application's responsibility.

1.3  Definitions, Templates, and Compilation

Author: Eike Stepper

Build a SQLTemplate without selecting a database connection. Compilation uses the adapter for SQL rendering and identifier quoting, and records an inferred DBType for each parameter occurrence when its schema context provides one. An explicit JDBC target type remains part of the parameter definition and is honored during binding. Default NULL binding is a later phase: when an inferred type is known, the adapter selects the JDBC NULL code through getJDBCTypeForNull(). Compilation cannot translate vendor-specific raw fragment text into another dialect. The same template can be compiled for another adapter.

2  Basic Statements

Author: Eike Stepper

The statement builders cover common SELECT and data-change forms. Keep values as parameters and represent tables and columns with schema metadata so the compiler can render identifiers for the selected adapter.

2.1  SELECT

Author: Eike Stepper

A SELECT projects fields or expressions. The example compiles a key lookup, binds the key, executes it, and closes both managed resources. The returned statement can be prepared again for another lookup.

2.2  INSERT and INSERT SELECT

Author: Eike Stepper

An explicit column list pairs each value with its named destination column. INSERT SELECT instead copies a query result into the target table; parameters in the SELECT remain ordinary compiled occurrences.

2.3  UPDATE

Author: Eike Stepper

An UPDATE names assigned fields in set() and limits affected rows with where(). The values are bound in rendered occurrence order: the new status first, then the order key.

2.4  DELETE

Author: Eike Stepper

A DELETE may omit its WHERE clause and affect every row. Prefer an explicit restrictive condition when removing a single record, as this key-based example does.

3  Queries and Composition

Author: Eike Stepper

Conditions, table references, subqueries, and fragments allow a query to be assembled from reusable parts. Structured elements retain metadata for rendering and binding; raw fragment text remains opaque to the compiler.

3.1  Conditions and Optional Filters

Author: Eike Stepper

Conditions are immutable values that can be named and combined before attaching them to a WHERE stage. The final condition tree determines SQL order and therefore positional binding order. Build only complete conditions, and add optional predicates only when their values are part of the request.

3.2  Aliases and Joins

Author: Eike Stepper

A SQLTableRef represents one occurrence of a table and can qualify its columns. Table aliases distinguish source columns in joins; aliases on projected expressions label output values instead.

3.3  Aggregates, Grouping, and HAVING

Author: Eike Stepper

Aggregate expressions can be projected and used in HAVING. This query groups orders by status and applies a parameterized minimum count after grouping. Aggregate and grouping support still depends on the target SQL dialect and adapter.

3.4  Subqueries

Author: Eike Stepper

A complete SELECT can be converted to SQLSubSelect and used in supported IN, EXISTS, or scalar contexts. Its parameters join the outer statement's rendered occurrence order. A subquery is preferable to raw SQL when the structured API can express the required shape.

3.5  SQL Fragments

Author: Eike Stepper

Fragments fill a gap when a query shape is not represented by the structured builders. Keep tables, columns, and parameter tokens structured inside a fragment. Raw text is neither parsed nor escaped, and must not contain question marks; represent every placeholder with a parameter token so occurrence metadata remains aligned with JDBC indexes.

4  Parameter Binding

Author: Eike Stepper

A logical parameter is a reusable identity in a definition; compilation creates one occurrence record for each place it appears in rendered SQL. The occurrence supplies the physical JDBC index and any type inferred from its local context. Binding APIs address values by JDBC order, JDBC index, or logical identity.

4.1  Fundamentals

Author: Eike Stepper

Sequential calls bind occurrence order. Indexed calls address one physical placeholder. Identity calls find all occurrences of the same SQLParameter object. These choices matter when a logical parameter is reused in different field contexts, because each physical occurrence can infer a different DBType.

4.1.1  Parameters and Occurrences

Author: Eike Stepper

Calling SQL.param() creates a logical parameter object. If that object is used twice, compilation creates two occurrences with separate JDBC indexes. A field comparison or field assignment may let the compiler infer a type for an occurrence. That type belongs to the occurrence, not to the logical parameter; the same identity can therefore have a VARCHAR occurrence and an INTEGER occurrence.

4.1.2  Positional and Identity-Based Binding

Author: Eike Stepper

Positional values are assigned in rendered JDBC order. Binding by JDBC index changes one occurrence, while binding by parameter identity changes every occurrence of that exact object in rendered order. The examples preserve the earlier customer lookup and repeated-identity patterns.

4.1.3  Sequential and Cursor-Based Binding

Author: Eike Stepper

bind() accepts a partial prefix and returns the number of values it bound. bindAll() requires the complete placeholder count. bindFrom() starts a partial sequence at a specified one-based index. A SQLParameterBinder owns an independent cursor: bind() advances after success, getNextIndex() reports the next JDBC position, skip() moves without binding, and from(index) repositions absolutely. The final legal position is parameter count plus one and accepts only an empty sequence.

4.2  Types and Default Binding

Author: Eike Stepper

The compiler infers a logical database type only when the occurrence is connected to a known field context, such as a direct field comparison, BETWEEN bound, or INSERT/UPDATE assignment. Arbitrary expressions, projections, and raw fragment tokens may not provide enough context. Explicit JDBC types can handle NULL where inference is unavailable.

4.2.1  DBType Inference

Author: Eike Stepper

Type inference is local to the compiled occurrence. A parameter assigned to a field or compared directly with a field inherits that field's DBType. BETWEEN uses the known field for both bounds. A parameter in an arbitrary projection or a fragment does not necessarily have an inferable type. For an untyped NULL, structured binding rejects the value if no occurrence type is available.

4.2.2  Default JDBC Setters

Author: Eike Stepper

Ordinary inferred values pass through CompiledStatement to IDBAdapter.bindParameter(). DBAdapter chooses a typed setter only for a supported DBType and compatible Java value. A non-NULL incompatible combination falls back to generic setObject(); it does not silently convert the Java value. Known-type NULL uses bindParameterNull() and getJDBCTypeForNull(). For unknown-type non-NULL values, Java-type dispatch is controlled by useJavaTypeForUnknownParameterType(), which defaults to false.

4.2.3  NULL and Explicit JDBC Types

Author: Eike Stepper

SQL.param(sqlType) stores a JDBC Types code. For a non-NULL value, the compiled statement calls setObject(index, value, sqlType); for NULL it calls setNull(index, sqlType). This is different from a custom SQLValueSetter: SQL.param(Types.BLOB) does not request PreparedStatement.setBytes(). Use a configured setter such as SQL.param(PreparedStatement::setBytes) when the complete binding operation must use that JDBC method.

4.3  Custom Binding Strategies

Author: Eike Stepper

A converter transforms an application value and leaves JDBC binding to the adapter. A setter receives the original value and performs the complete JDBC operation. Call-specific strategies override configured ones for one operation. The diagram shows how CompiledStatement resolves those strategies before default binding.

4.3.1  Value Converters

Author: Eike Stepper

A converter maps a non-NULL application value to the value supplied to default binding. NULL input bypasses conversion and follows the occurrence's explicit or inferred JDBC NULL typing. Converter exceptions propagate to the caller.

4.3.2  SQLValueSetter

Author: Eike Stepper

A configured or explicit SQLValueSetter owns the full JDBC operation and receives the original application value, including NULL. It bypasses converter and adapter binding for that occurrence. The default byte-array mapping covers BINARY, VARBINARY, and LONGVARBINARY, not BLOB. SQL.param(Types.BLOB) selects explicit target typing through setObject(..., Types.BLOB) or setNull(..., Types.BLOB); it does not select setBytes(). An explicitly configured SQLValueSetter guarantees the chosen JDBC operation and can be useful for driver-specific BLOB compatibility, although drivers do not universally require setBytes() for BLOB.

4.3.3  Overrides and Precedence

Author: Eike Stepper

A call-specific setter runs first and receives the original value. Otherwise a call-specific converter, when supplied, transforms the value and takes precedence over a parameter-configured setter. Without a call-level strategy, the configured setter runs before a configured converter. If no setter handles the value, the explicit JDBC type controls typed setObject/setNull; otherwise default adapter binding handles it. Converters are applied only to non-NULL values. A setter and converter cannot both be configured on one SQLParameter.

The order in this table is precedence for one binding operation. A selected setter performs the complete operation and exits the default path.

OrderStrategyEffect

An explicit converter therefore overrides a configured setter for that call, while a call-specific setter overrides both. Explicit JDBC types apply only when a setter has not already handled the value.

4.3.4  SQLDefaultSetter

Author: Eike Stepper

An SQLDefaultSetter receives a statement and JDBC index, but no application value. It performs the complete binding operation for an implementation-defined default. That default is not necessarily NULL or the SQL column's DEFAULT expression. It may be a domain value such as an empty byte array. This strategy is separate from binding a supplied value through SQLValueSetter or the default adapter path.

5  DBAdapter Customization

Author: Eike Stepper

IDBAdapter.bindParameter() is the public binding hook used for ordinary bindings. Its interface default is deliberately generic for independent implementations. DBAdapter supplies a typed implementation and protected per-setter extension points for adapters that need to change one JDBC operation without replacing the type-dispatch algorithm.

5.1  Default Binding Architecture

Author: Eike Stepper

The SQL definition assigns values to logical parameters. Compilation records each physical occurrence and its inferred DBType. CompiledStatement applies selected converters, handles explicit JDBC target types, and delegates every remaining value, including typed NULL, to IDBAdapter.bindParameter(). The generic interface default uses setObject except for known-type NULL, which uses getJDBCTypeForNull(). DBAdapter dispatches supported compatible pairs to typed setters. This keeps occurrence logic in the compiler and JDBC customization in the adapter.

The diagram shows the adapter's independent default-binding decisions, including its direct-call handling for unknown-type NULL and the opt-in Java-type fallback for unknown non-NULL values.

5.2  Unknown Parameter Types

Author: Eike Stepper

DBAdapter.useJavaTypeForUnknownParameterType() defaults to false. Under that conservative policy, an unknown non-NULL value uses setObject. If enabled, supported Java scalar classes select the same typed hooks used for known compatible DBType/value pairs; unsupported classes still use setObject. The policy does not change known-type dispatch, and unknown NULL remains generic object binding at the adapter level. Structured DML separately rejects unknown untyped NULL before delegation.

5.3  Protected Binding Extension Points

Author: Eike Stepper

DBAdapter exposes exactly twelve protected overridable methods. The default implementation makes the matching JDBC call. Most adapters need no override; a database-specific adapter can change one operation while retaining the common mapping and fallback behavior. The Boolean example is hypothetical: it models a backend whose Boolean values are represented as integer 0/1 parameters. The H2Adapter subclass is a concrete, compilable illustration of the extension mechanism; it does not imply that H2 generally requires integer Boolean binding. Adapters should normally retain setBoolean() unless their backend or driver gives a concrete reason to change it.

6  Statement Lifecycle and Reuse

Author: Eike Stepper

Reuse the adapter-neutral template or compiled statement across operations. Prepare and close a managed JDBC statement for each checkout so its connection can return the statement to its cache and release associated resources.

6.1  Templates and Compiled Statements

Author: Eike Stepper

A template captures the builder's immutable definition. The adapter-specific compiled statement retains its SQL and occurrence metadata, but no connection or prepared statement. Reuse either definition for repeated executions.

6.2  Preparing, Executing, and Closing

Author: Eike Stepper

Preparing checks out a connection-bound managed statement. Use try-with-resources for that statement and any result set. The connection's cache may reuse the JDBC object after close; ReuseProbability is a cache hint and does not guarantee object identity.

6.3  Partial Binding and Statement Reuse

Author: Eike Stepper

Partial binding changes only the positions supplied in that operation. Untouched positions may still contain values from an earlier use of a reused JDBC statement. Rebind every position required by the next execution. Range and value-count checks happen before a sequence starts, but a later setter failure does not roll back earlier JDBC side effects.

7  Portability and Limitations

Author: Eike Stepper

The compiler renders operations represented by the structured API and delegates identifier quoting and typed binding behavior to the adapter. It does not rewrite arbitrary fragment text, validate business rules, map result rows to objects, infer every parameter type through arbitrary expression trees, or generate DDL. SQL syntax and join support remain bounded by the adapter and target database. Keep portable portions structured and isolate vendor-specific syntax where it is needed.
